Design Decisions

Choices made where the spec was silent or ambiguous.

Design Decision
PHASE_HANDOFFS table pre-filled in layer1 template
templates/layer1-global-map-template.html
The spec defines <!-- ##PHASE_HANDOFFS## --> as a marker for AI to fill. I pre-filled the five standard rows (Phase 1–5 → artifact → purpose) in the template itself, and kept the marker below the pre-filled rows as an extension point.

Rationale: The handoffs table is static — it describes the fixed architecture of the workflow, not dynamic scan data. Pre-filling avoids AI having to regenerate the same boilerplate every run, while the marker remains for AI to append project-specific entries if needed.
Design Decision
step3 reads each file twice (Phase 1 + Phase 2), not cached
scripts/step3-dead-scan.ps1
The spec calls for O(N+M) performance. My implementation reads each .cs file twice: once in Phase 1 to collect method definitions, once in Phase 2 to count tokens. This is 2N file reads, not cached.

Rationale: Caching all file content in Phase 1 (to reuse in Phase 2) would require holding the full text of thousands of files in memory simultaneously. For a 5M LOC codebase this could easily exceed 1–2 GB. 2N file reads with O(1) memory per file is the safer tradeoff. The token-counting loop in Phase 2 is still O(N+M) in the algorithmic sense — each file is scanned once, each token checked against a HashSet in O(1).
Design Decision
BaseClass/Interfaces split uses "starts with I" heuristic
scripts/layer2-step1-api.ps1
When parsing public class Foo : Bar, IBaz, IQux, I split inheritance into BaseClass vs Interfaces by treating the first item that does not start with a capital I as the BaseClass.

Rationale: Roslyn-accurate parsing is out of scope for a regex-based script. The convention in C# (and the WinForms ecosystem specifically) is that interface names begin with I. This heuristic correctly handles the most important case: : Form, : UserControl, : Panel. Known failure modes: classes inheriting from a non-I-prefixed interface (rare in WinForms), or Microsoft.Win32.RegistryKey-style qualified names. These will be silently mis-categorised.
Design Decision
LOC is calculated by brace-counting, not line-counting from declaration end
scripts/layer2-step1-api.ps1
Method LOC is computed by finding the opening { after the method signature, then tracking brace depth to find the matching }. Line count of that range = LOC.

Rationale: This handles nested lambdas and anonymous methods correctly in most cases. Known failure mode: string literals or comments containing unbalanced braces will corrupt the depth counter. For a quick approximation in a Phase 0 scan this is acceptable; Roslyn would be needed for exact results.
Design Decision
step0-preflight uses framework attribute fallback chain
scripts/step0-preflight.ps1
To extract target framework, I try three XML paths in order: //TargetFramework → //TargetFrameworks → //TargetFrameworkVersion. The first covers SDK-style projects, the second multi-targeting, the third old-style .csproj (which WinForms legacy codebases typically use).

Rationale: A 5M LOC WinForms codebase is almost certainly on old-style csproj format using TargetFrameworkVersion v4.x. The fallback chain handles both old and new formats without requiring the user to specify which format they have.
Design Decision
API section in Layer 2 HTML collapses the entire section, not just individual rows
templates/layer2-module-report-template.html
The spec says "API 表格改為預設收合". The existing template already had individual rows collapsed (expand on click). I added a section-level toggle that hides the entire API table block by default, in addition to keeping row-level expand.

Rationale: A module with 200+ APIs would show a very long collapsed-row table even when individual rows are closed. Hiding the whole section by default makes the Decision Recommendation and coupling data visible without scrolling.
Design Decision
Layer 2 nav link updated to ../00-global-map.html
templates/layer2-module-report-template.html
The original template linked back to 00-global-map.html (same-directory). Since Layer 2 reports now live in .analysis/{ModuleName}/, the link must go up one level: ../00-global-map.html.

This is a direct consequence of the new folder structure defined in the spec.
Design Decision
step1 and step2 output paths updated even though not listed in the change manifest
scripts/step1-dependency-map.ps1 · scripts/step2-git-stability.ps1
The spec's "第六層：檔案異動清單" does not list step1 or step2 as files to change. However, those scripts output to docs/archaeology/tmp/, while the entire spec mandates .analysis/tmp/ as the output root. I updated their output paths for consistency.

Not updating them would have broken the Layer 1 flow: step1 and step2 would write to the wrong folder, and subsequent AI analysis steps (which read from .analysis/tmp/) would fail.
Deviations

Places where I intentionally departed from the spec, and why.

Deviation
coupling-in.csv logic inverted from spec — currently tracks INTRA-module coupling, not INCOMING callers
scripts/layer2-step2-usage.ps1
Spec intent (as I now read it): For each class name in api.json, search external files for new ClassName( or : ClassName patterns. Record whether the referencing file is in the same project as the target (SAME_PROJECT) or a different project (OTHER_PROJECT). SAME_PROJECT entries are the "extraction blockers" — files in the same project that depend on the target's types, making it hard to split the target out.

What I implemented: I scan internal files (inside the target folder) for usages of the target's own class names. All entries get SAME_PROJECT. This is intra-module coupling, not incoming coupling from outside.

Consequence: The coupling-in table will show the target module's own internal class references rather than external callers. The "SAME_PROJECT extraction blocker" signal will be incorrect.

Correct implementation should be: Scan all files outside scanFolder; for each file, check if any api.json class name appears; record DependencyScope as SAME_PROJECT if the external file's .csproj is in the same directory tree as the target's .csproj, otherwise OTHER_PROJECT.
Deviation
Removed the per-module warn-box before the API table; added a generic one at footer
templates/layer2-module-report-template.html
The original template had a specific warning: "this module has {{DOWNSTREAM_COUNT}} downstream projects, may be referenced externally via dll — run Task A first." I removed it and replaced with a generic footer warning.

Reason: With the Decision Recommendation card now at the top containing the same evidence, having a module-specific warning mid-page before the API table created redundancy and interrupted the flow from coupling-in → vitality → API. The footer warning covers the same concern without interrupting the analysis flow.

Risk: Engineers who jump directly to the API table might miss the DLL-reference caveat. Mitigated by the Decision Recommendation card at the top which should be read first.
Deviation
SKILL.md does not specify the script repo path; uses relative path notation from spec verbatim
SKILL.md
The spec's format example uses .\.github\skills\csharp-archaeology\scripts\step0-preflight.ps1. This path only resolves correctly if the user's CWD is the skill repo root — which is not the case when analyzing an external C# codebase.

What I did: Used the path verbatim as specified. I did not add any path-resolution logic or instructions for multi-root workspace setup.

Risk: When Copilot runs the skill against an external C# workspace, the paths will not resolve. Users will need to either (a) copy the scripts to their workspace, or (b) configure a multi-root VS Code workspace. This is an unresolved operational concern that should be addressed in a follow-up.
Tradeoffs

Alternatives considered and why I picked what I did.

Tradeoff
REFLECTION risk flag: double-quote string match only (not Roslyn nameof)
scripts/step3-dead-scan.ps1
Option A (chosen): Flag as REFLECTION if the method name appears in any double-quoted string literal anywhere in the file. Simple regex, fast.

Option B: Also check nameof(MethodName) — a compile-safe alternative to string literals for reflection. This is common in modern C# but less so in legacy WinForms.

Chose A because: Legacy WinForms codebases predate nameof (C# 6). The false-positive rate from quoted strings is acceptable for a Phase 0 scan. Engineers reviewing LOW-confidence candidates will see the REFLECTION flag and know to inspect manually.
Tradeoff
vitality.csv uses file-level git log, not project-level
scripts/layer2-step2-usage.ps1
Option A (chosen): Run git log per file inside the target folder. Gives file-level granularity.

Option B: Run one git log on the whole target folder (like step2-git-stability.ps1 does). Much faster, but loses per-file detail.

Chose A because: The vitality rows in the HTML are per-file heat bars. File-level data is required. The spec explicitly lists File as a column in vitality.csv. The performance cost is bounded by the number of files in the target module (typically small for a single module deep-dive).
Tradeoff
step3 FullyQualifiedName uses last-seen class before method, not true enclosing class
scripts/step3-dead-scan.ps1
Option A (chosen): Find the last class ClassName match in the text before the method declaration. Simple, no AST needed.

Option B: Parse brace depth to find the truly enclosing class. More accurate but significantly more complex to implement in regex-only PowerShell, and fragile for nested classes.

Chose A because: For NDepend cross-reference purposes, the FQN will be correct in the common case (one class per file, or methods after the class they belong to). Nested-class FQNs will be wrong, but nested classes are rare in legacy WinForms. The FQN is a Phase 2 cross-reference aid, not a deletion criterion.
Tradeoff
Layer 2 HTML has 6 sections, not the original 3 — adds scroll depth
templates/layer2-module-report-template.html
Adding Decision Recommendation (top) + Coupling-In + Vitality takes the page from 3 sections to 6 and significantly increases scroll depth.

Mitigation applied: Decision Recommendation is pinned to the top (30-second read target); API table is collapsed by default (removes the largest scrollable content from default view); coupling-in and vitality are positioned before the API table (higher priority than raw API list).

Alternative not taken: Tabbed interface (Decision | Coupling | Vitality | API). Tabs would require more JS and deviate further from the existing template style. The single-scroll layout with section headings and the sec-num counter (01/06…06/06) gives engineers a mental map of depth.
Open Questions

Anything that should be confirmed or revised before this skill is used in production.

Open Question
coupling-in.csv: should it be fixed before use?
scripts/layer2-step2-usage.ps1
As documented in Deviations, the current coupling-in logic is inverted. The intended logic is: scan external files for references to the target's classes; classify as SAME_PROJECT or OTHER_PROJECT based on whether the external file shares the same .csproj boundary as the target.

Questions for you:
  1. Is my re-interpretation of "coupling-in" correct — i.e., it measures incoming dependencies from external files, not internal self-references?
  2. Should "SAME_PROJECT" mean "same .csproj file" or "same physical folder tree"? For subfolder mode (-ModulePath), the target and its callers may share the same .csproj.
  3. Should I fix this in a follow-up pass, or is the current (inverted) behaviour acceptable for a first iteration?
Open Question
Script path resolution for multi-root VS Code workspace
SKILL.md
The SKILL.md execution commands assume the script path .\.github\skills\csharp-archaeology\scripts\ is resolvable from the target C# workspace CWD. This only works if the skill repo is the active workspace root, not when analyzing an external codebase.

Questions for you:
  1. Is the intended usage model that users copy the scripts into their target workspace?
  2. Or is this a VS Code multi-root workspace setup where both repos are open simultaneously?
  3. Should SKILL.md include setup instructions for one of these models?
Open Question
Build command inference in copilot-instructions-draft.md
SKILL.md — Phase 0 Synthesis
The spec says the AI should write the build command by reading preflight-report.json. The preflight script captures slnFiles (an array of .sln filenames), but not the actual build command (e.g., MSBuild path, custom bat files, NuGet restore steps).

Question for you: Should I add detection of common build artifacts to step0-preflight.ps1 — e.g., check for build.bat, Makefile, Directory.Build.props, or infer from CI config files — so the AI has better raw material to write the build command?
Open Question
Tier table: how many rows to show?
templates/layer1-global-map-template.html
The TIER_TABLE marker comment in the template doesn't specify a row limit. For a 100+ project codebase, a full Tier table would be enormous.

Question for you: Should the SKILL.md AI analysis instructions specify a row limit (e.g., "show all TIER-1, Top 10 TIER-2, omit TIER-3")? Or should the table always show all projects and rely on browser scrolling?
Open Question
step3 performance for LARGE tier: is 15–30 min acceptable?
scripts/step3-dead-scan.ps1
The preflight time estimate for a LARGE codebase (100+ projects) is 15–30 min for step3. The O(N+M) token-counting loop is still O(N × avg_tokens) in absolute terms, and PowerShell's regex engine is single-threaded.

Question for you: Is 15–30 min acceptable for your team's workflow? If not, I can explore a parallel-jobs approach using PowerShell ForEach-Object -Parallel (PS 7+) or splitting the work into chunked runs. This would require knowing what PowerShell version the target environment has.
