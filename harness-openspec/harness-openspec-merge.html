融合設計 · learn-harness × OpenSpec

兩套流程，無縫接成一套

learn-harness-engineering 給「執行控制層」，OpenSpec 給「規格層」。它們只在一個地方重疊，補上彼此都缺的硬關卡，就能合成一條從規格到綠燈、擋得住的流水線。範例：C# WinForms 折扣計算機。

一句話設計原則

兩套流程互補，不重複。融合的關鍵動作只有三個：一個 router、一份清單、一道硬關卡。

01

調研結論：誰帶來什麼

先看兩邊各自的真實角色（基於 repo 實際內容）。一個偏 infra/執行，一個偏規格/需求。

walkinglabs/learn-harness-engineering
執行控制層（偏 infra）
  • init.sh：把 install / check / test / build 裝進一支腳本（真實的機械檢查包）
  • feature_list.json：機器可讀的功能清單 + 狀態（not_started→active→passing）
  • AGENTS.md：router，每次 session 先讀它
  • session 生命週期：progress.md、session-handoff、clean-state checklist
  • 五子系統：指令 / 狀態 / 驗證 / 範圍 / 生命週期
Fission-AI/OpenSpec
規格層（偏需求）
  • artifact 圖：proposal.md → spec.md → design.md → tasks.md
  • spec.md：### Requirement: SHALL… + #### Scenario:（GIVEN/WHEN/THEN）
  • openspec validate --strict：規格結構的硬關卡（沒 scenario 就報錯）
  • 生命週期：/opsx:propose → apply → verify → archive
  • openspec init --tools github-copilot 產生 .github/prompts/ slash 指令
02

重疊、互補、衝突

把元素逐一對齊，會發現它們只在一個地方真正重疊，其餘多是互補，還有一個兩邊都缺的洞。

重疊（同一件事，兩種格式）

feature_list.json ＝ tasks.md

兩者都是「被追蹤的清單 / 進度狀態 / 完成定義」。直接並用會讓 agent 不知道看哪個 → 狀態漂移。必須二選一。

重疊

兩個 AGENTS.md router

兩邊都堅持「agent 先讀 AGENTS.md」。OpenSpec 自己也會產生一份。內容要合併，不能各擺一份。

互補（OpenSpec 補洞）

真正的規格層

learn-harness 只有「每功能一條 verification 指令」，沒有 SHALL / GWT scenario。OpenSpec 補上可讀又可驗的需求。

互補（learn-harness 補洞）

機械化 compile/test 包

OpenSpec 的 validate 只查 markdown、verify 是 LLM 判斷，都不跑真實程式。init.sh 補上真的會編譯、會跑測試的那層。

兩邊都缺的洞 ⚠️

硬 / 確定性約束層（git hook、CI）

更關鍵的是——兩邊原生都是軟關卡。init.sh 靠 agent 自己願意跑、/opsx:verify 只查 checkbox、archive 對未完成只警告不擋。必須補一道 agent 繞不過的硬關卡。

03

融合設計：一個 router、一份清單、一道硬關卡

RESOLVE 重疊 #1

一份清單

退役 feature_list.json，tasks.md 當唯一清單。原本三個欄位各有去處：意圖→spec.md 的 Requirement；verification→Reqnroll scenario→一條 dotnet test --filter；狀態→tasks.md 的 checkbox。

RESOLVE 重疊 #2

一個 router

留一份 AGENTS.md（OpenSpec 擁有、會重生），把「本機 init.sh / Husky 指令」寫進 openspec/config.yaml 的 context:，讓重生時保留。

FILL 那個洞

一道硬關卡

Husky.NET pre-commit：commit 前強制跑 openspec validate --strict + dotnet format + dotnet test，沒過就擋。CI 再鏡射一次。這是兩邊都缺、最重要的一步。

💡 為什麼 Husky.NET 能補洞？因為它綁在 git commit 事件上，不靠 agent 自律——這正是 init.sh「希望 agent 會跑」做不到的。同樣的檢查，從「建議」升級成「約束」。

融合後的專案長相

# 規格層（OpenSpec 擁有，唯一真相）
openspec/
├── specs/pricing/spec.md          # 已建成：SHALL + GWT
├── changes/add-price-calculator/
│   ├── proposal.md  design.md
│   └── tasks.md                   # 唯一清單（feature_list.json 已退役）
└── config.yaml                    # context: 注入 init/Husky 規則

# 執行 / 約束層
AGENTS.md                          # 唯一 router
.husky/task-runner.json            # 硬關卡：commit 前強制跑
scripts/dev-bootstrap.sh           # 原 init.sh，降為非權威
.github/prompts/*.prompt.md        # OpenSpec 產生的 Copilot 指令

# 程式 + 測試
src/Pricing/PricingService.cs      # 純邏輯，不碰 WinForms（MVP）
src/UI/MainForm.cs                 # Passive View，只顯示
tests/Pricing.Tests/Features/Pricing.feature   # Reqnroll GWT
📌 一眼看出融合點：規格在 openspec/、清單只剩 tasks.md、router 只剩一個 AGENTS.md、硬關卡在 .husky/。原本 learn-harness 的 init.sh 沒消失，只是從「權威」降為「Husky 會去呼叫的腳本」。
05

融合後的完整生命週期（軟/硬關卡標示）

綠＝硬關卡（機器擋得住）；紅圈＝軟關卡（只警告，靠後面的硬關卡兜底）。

1

Copilot 打 /opsx:propose add-price-calculator軟

產生 proposal/design/tasks/spec.md。spec.md 用 EARS + GWT，tasks.md 一個 scenario 一個 checkbox。

2

openspec validate --strict硬

規格結構沒 scenario 就報錯、回傳非零。注意：它只查結構，不查行為。

3

加 Reqnroll .feature，先看紅燈硬

每個 Scenario 鏡射成測試，實作前先跑 → 紅燈（Kent Beck 紅燈先行）。

4

/opsx:apply 邊做邊勾 checkbox軟

只有對應 dotnet test --filter 綠了才把 [ ] 打成 [x]。

5

git commit → Husky.NET pre-commit硬

強制跑 format + validate --strict + dotnet test。失敗就擋下 commit，agent 根本送不出壞東西。這是整條線的命門。

6

/opsx:verify 報完成度軟

LLM 審查（主要看 checkbox），給人類參考。真正的失敗早在第 5 步被擋掉了。

7

/opsx:archive 併入 specs/軟

把 delta 合進 openspec/specs/。對未完成只警告——但有第 5 步兜底，無妨。

8

定期 dotnet stryker硬

突變測試當「否證器」。存活的突變＝你漏寫的 scenario → 回頭發一個新的 /opsx:propose，讓規格層吸收。

🔬 第 8 步收束整個哲學：存活的突變，就是「你無法讓它失敗」的標準——也就是漏掉的需求。把它當成新 scenario 補回 spec.md，而不是隨手加個測試。能被否證，才是真標準。
06

範例：折扣計算機的規格（EARS + GWT）

openspec/changes/add-price-calculator/specs/pricing/spec.md
## ADDED Requirements

### Requirement: Discount calculation
# EARS：Event-driven + Unwanted behaviour
WHEN a discount is applied to a positive base price,
the system SHALL return a non-negative final price.
IF the base price is negative, THEN the system
SHALL reject the calculation with an error.

#### Scenario: Standard discount
- GIVEN a base price of 100.00
- WHEN a discount of 20 percent is applied
- THEN the final price is 80.00

#### Scenario: Reject negative price
- GIVEN a base price of -5.00
- WHEN a discount of 10 percent is applied
- THEN the calculation is rejected with an error
.husky/task-runner.json （硬關卡：commit 前強制）
{
  "tasks": [
    { "group":"pre-commit", "command":"dotnet",
      "args":["format","--verify-no-changes"] },
    { "group":"pre-commit", "command":"openspec",
      "args":["validate","--changes","--strict"] },
    { "group":"pre-commit", "command":"dotnet",
      "args":["test","--no-restore"] }
  ]
}
# 任一非零退出 → commit 被中止
帶走這一句

OpenSpec 給規格，learn-harness 給執行，
但兩邊都只是軟關卡。
真正讓它成立的，是你補的那道commit 前硬關卡。

一個 router、一份清單、一道硬關卡。
融合不是把兩套疊在一起，是消除重疊、補上彼此的洞。🌱
