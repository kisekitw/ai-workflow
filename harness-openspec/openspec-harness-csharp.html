Harness Engineering · 實戰範例

spec.md 怎麼確保被符合？
一個 C# WinForms 小範例

折扣計算機 · OpenSpec 寫規格 · GitHub Copilot 寫程式 · Reqnroll 把 GWT 變成會跑的測試。重點：怎麼讓「AI 說做完了」變成「機器擋得住的證據」。

OpenSpecGitHub CopilotC# / WinFormsReqnrollStryker.NET
這份範例要回答的一句話

spec.md 只是一份「使用者要什麼」的文件。它本身擋不住任何東西。
Harness 的工作，是在它周圍疊四道關卡，讓「不符合規格的程式」根本進不了 main 分支。

00

範例功能：折扣計算機

輸入原價與折扣百分比，算出最終價格；不合理的輸入要被拒絕。小，但五臟俱全——足以走完整條 spec → 測試 → 實作 → 驗收。

💡 WinForms 的關鍵設計：把所有邏輯放進一個純 C# 的 PricingService 類別，Form 只負責顯示（Passive View / MVP）。因為 WinForms 的視窗很難直接做單元測試，把邏輯抽出來，整條規格就能在「不開視窗」的情況下被測。這是有所本的標準做法（MSDN「Model-View-Presenter」）。
01

用 OpenSpec 寫 spec.md（GWT 的真實格式）

在 Copilot Chat 跑 /opsx:propose，OpenSpec 幫你建資料夾，你填寫規格。注意真實語法：SHALL/MUST 要放在需求內文、每個需求至少要有一個 #### Scenario:。

openspec/changes/add-price-calculator/specs/pricing/spec.md
## ADDED Requirements

### Requirement: Discount calculation
The system MUST compute a non-negative final price given a
positive base price and a discount percentage between 0 and 100.

#### Scenario: Standard discount
- GIVEN a base price of 100.00
- WHEN a discount of 20 percent is applied
- THEN the final price is 80.00

#### Scenario: Reject negative price
- GIVEN a base price of -5.00
- WHEN a discount of 10 percent is applied
- THEN the calculation is rejected with an error
02

第一道硬關卡：規格結構驗證

跑 openspec validate add-price-calculator --strict。如果你漏了 scenario、或忘了 MUST，它直接報錯、回傳非零、擋住 archive。這不是建議，是機器判定。

$ openspec validate add-price-calculator --strict
✗ [ERROR] requirements[0].scenarios:
          Requirement must have at least one scenario
# 退出碼非 0 → 這個 change 無法被 archive 進 specs/
💡 這道關卡守的是「規格本身寫得對不對」——還沒碰到程式。連需求都長歪了，後面全是白工。
03

把每條 Scenario 變成會跑的測試（紅燈先行）

spec.md 的每個 Scenario，鏡射成 Reqnroll 的 .feature 檔；GWT 綁定到 C# 步驟方法（對應 Arrange-Act-Assert）。關鍵紀律：在實作之前就寫測試，先看它紅燈——這是 Kent Beck 的 Red→Green→Refactor。

Pricing.feature  (Gherkin，鏡射 spec.md)
Feature: Discount calculation

Scenario: Standard discount
    Given a base price of 100.00
    When a discount of 20 percent is applied
    Then the final price is 80.00
PricingSteps.cs  (GWT → Arrange / Act / Assert)
[Binding]
public class PricingSteps
{
    private decimal _basePrice;
    private decimal? _result;
    private readonly PricingService _svc = new();

    [Given("a base price of (.*)")]
    public void GivenPrice(decimal p) => _basePrice = p;   // Arrange

    [When("a discount of (.*) percent is applied")]
    public void WhenApplied(decimal pct)                  // Act
        => _result = _svc.ApplyDiscount(_basePrice, pct);

    [Then("the final price is (.*)")]
    public void ThenPrice(decimal expected)               // Assert
        => Assert.Equal(expected, _result);
}
💡 跑 dotnet test → 編譯失敗，因為 PricingService 還不存在。這個失敗是好事——它證明了「這個測試真的會抓錯」。接著才讓 Copilot 寫實作，把燈轉綠。
📌 為了精簡，上面只展示了第一個 scenario。 真正照規矩做時，spec.md 裡的兩個 scenario 都必須各有對應測試（包含「拒絕負數價格」那條）——「每個 Scenario 都要有測試」正是第 4 層關卡會檢查的鐵律。
04

四道關卡：哪些是「建議」，哪些是「約束」

這是整份範例的核心。只有第 1 層是 AI 自由心證（建議），第 2~4 層都是機器擋得住（約束）。

① 指令層

建議 · 非確定性

三種來源的指令疊在這一層：copilot-instructions.md（你手寫的規矩）、AGENTS.md（通用 agent 指令），以及 .github/prompts/——這是 OpenSpec 在 openspec init --tools github-copilot 時自動寫進去的，把 /opsx:propose 等指令變成 Copilot Chat 看得到的 slash command。這層告訴 Copilot 規矩——但 GitHub 官方明說「AI 不保證每次都照做」，所以不能只靠它。

② 規格結構關卡

約束 · 確定性

openspec validate --strict。規格寫歪就回傳非零、擋住 archive。機器判定，不看臉色。

③ 可執行規格關卡

約束 · 確定性

Reqnroll 把每個 Scenario 變成測試，dotnet test 紅燈就是紅燈。AI 沒辦法用嘴把紅燈說成綠的。

④ 程式約束關卡

約束 · 確定性

TreatWarningsAsErrors（警告當錯誤、編譯失敗）、Husky.NET、GitHub Actions CI。Husky.NET 是什麼？它是 Git pre-commit 鉤子的安裝器——讓你在 git commit 真正發生之前自動跑一串檢查（dotnet test、dotnet format、openspec validate），任一個失敗就擋下這次 commit，程式碼進不了版控。任一關卡紅燈 → PR 合不進去。

同樣的檢查，差別在「靠 AI 自律 vs 靠事件強制」

有人問：那 init.sh + AGENTS.md（把 compile/clean/test 裝進腳本、用 AGENTS.md 當 router 每次提醒 agent 去跑）跟 Husky.NET 是同一回事嗎？封裝的意圖相同，但硬度差一級——這就是「建議 vs 約束」。

建議 · 可繞過

AGENTS.md → init.sh

  • 靠 agent 自己「願意」讀 AGENTS.md、自己決定去跑腳本
  • context 滿了、或它覺得「應該沒問題」就可能跳過
  • 觸發權在 AI 的判斷
  • 譜系位置：規則文件那一格（持久、但建議性）
約束 · 不可繞過

Husky.NET（git hook）

  • 綁在 git commit 事件上，不問 agent 願不願意
  • 一下 commit 就強制執行，沒過就擋，跳不掉
  • 觸發權在 Git，不在 agent
  • 譜系位置：Hooks 那一格（持久、強制性）
💡 init.sh 是最入門、跨語言通用的做法（教學常用）；Husky.NET 是把同樣的意圖升級成 git 層級的硬約束。能看出這兩個是「同一意圖、不同硬度」，就抓到約束層的精髓了。
05

「事先凍結、可驗證的合約」具體長怎樣？

前面說「過關標準要事先凍結、可驗證，否則 AI 會無限互吵」。在 OpenSpec 裡，這份合約有個真實的落腳處：tasks.md——一份打勾清單，AI 邊做邊勾。好的寫法是每個任務都附上 Acceptance（過關條件） 和 Evidence（證據），把「夠好」釘成機器能查的東西。

openspec/changes/add-price-calculator/tasks.md
## 1. 折扣計算邏輯
- [ ] 1.1 實作 PricingService.ApplyDiscount
      Acceptance: Pricing.feature 兩個 scenario 全綠
      Evidence:   dotnet test 全過 + Stryker 突變分數 ≥ 80%
- [ ] 1.2 拒絕負數價格 / 百分比超出 0~100
      Acceptance: 非法輸入時擲出例外，且有對應測試
      Evidence:   測試 ThenRejected 綠燈
💡 重點不在格式，在「Acceptance 與 Evidence 必須是可驗證的」。寫「程式碼要優雅」→ 無限互吵；寫「兩個 scenario 全綠 + 突變分數 ≥ 80%」→ 達標就是達標，合約說了算，不是「最後一個說話的 AI」說了算。可測試的驗收標準有個方法叫 EARS（Rolls-Royce 2009），值得查。
📌 AI 之間吵不出結果時怎麼辦？ 那不是「再叫一個 AI」的時機，是合約寫漏了的訊號 → 停下來，人類把這條補進 spec.md / tasks.md、凍結它、再重來。裁判權永遠在人手上——這就是你前面答對的「UI 顏色沒定義在 spec.md，就由人當下裁決要不要補」。

顆粒度 = 可驗證性（同一個問題的兩面）

為什麼有時候 task 寫不出好的 Acceptance/Evidence？因為 task 切得太粗。「task 顆粒度」和「能不能寫出可驗證 Evidence」其實是同一個問題——一條 task 能不能被一個測試釘住，就是在問它夠不夠單一明確。

✗ 顆粒太粗
- [ ] 實作折扣計算機

Evidence 只能寫「能跑就好」。因為它包了太多行為，沒有單一的 pass/fail。

✓ 顆粒剛好
- [ ] 標準折扣：100 打 8 折 = 80

Evidence 立刻寫得出：dotnet test --filter discount_standard。因為它對應恰好一個可驗證行為。

💡 判斷 task 切得對不對，有個簡單測試：試著替它寫一條 Evidence 指令。寫得出 → 顆粒剛好；寫不出、只能寫形容詞 → 太粗，該再拆。

怎麼確認一條 Acceptance「可被驗證」？三問 + 紅燈確認法

拿任何一條 Acceptance，問三個問題。任一個答不出來，它就還不夠格當硬關卡。

1

觸發是什麼？對應 WHEN / IF

「當輸入 100 和 20%」。答不出明確觸發 → 太模糊。

2

預期的具體結果是什麼？對應 THEN

「回傳 80.00」。如果結果是「正確」「正常」這種形容詞、不是能比對的具體值或狀態 → 不可驗證。

3

我能寫出一條跑完明確回傳通過/失敗的指令嗎？

「dotnet test --filter discount_standard」。如果發現「要人看畫面才知道」「要主觀判斷美醜」→ 它不該是硬關卡，頂多是建議。

🔬 最殘酷也最有效的確認法：紅燈先行。 先把這條 Acceptance 寫成一個會失敗的測試，跑它，看它真的紅。如果你連「讓它紅」都做不到——不知道怎麼讓這條件失敗——就證明它不可驗證。一條無法失敗的標準，就是一條無法驗證的標準。這跟 Stryker「把程式改壞看測試會不會紅」是同一個哲學：能被否證，才是真標準。

何時產出？何時驗證回填？

A

產出：/opsx:propose（寫程式之前）

OpenSpec 自動產生 tasks.md 的打勾骨架。但 Acceptance / Evidence 不是它自動填好的——要你或 AI 在這階段補上、並凍結。

B

回填：/opsx:apply（實作時）

AI 邊做邊勾 checkbox。做完後 /opsx:verify 做一次「自動同儕審查」，回報 CRITICAL / WARNING / SUGGESTION。

⚠️ 誠實的限制（這正是你最該警惕的）：有所本地說，/opsx:verify 的完成度檢查主要看「checkbox 有沒有打勾、格式對不對」（用 regex 找打勾符號），/opsx:archive 對未完成任務也只警告、不阻擋。換句話說——OpenSpec 驗的是「你說做完了沒」，不是「你真的做到了沒」。AI 大可把勾打滿、verify 照樣過。所以 OpenSpec 的 verify/archive 是軟關卡（建議層）。

怎麼確保 AI 寫的 Acceptance/Evidence「可驗證」？

一條鐵律：Evidence 必須是一條能貼進終端機跑、會回傳通過/失敗的指令。把它接到 dotnet test / Stryker / CI——讓機器當裁判，而不是讓 OpenSpec 信任 checkbox。這就是把軟關卡變硬關卡的關鍵動作。

✗ 不可驗證（AI 很愛這樣寫）

Acceptance: 折扣計算正確、運作正常

誰來判斷「正確」「正常」？這是廢話——勾打了也沒人能反駁，等於沒關卡。

✓ 可驗證
dotnet test --filter Category=discount dotnet stryker → 突變分數 ≥ 80%

機器跑、回傳碼說話。過不了 → CI 紅燈 → 合不進去。

💡 過濾器：如果一條 Acceptance 沒辦法被翻成一條會 pass/fail 的指令，它就還不夠格凍結——要嘛改寫成可跑的，要嘛承認它只是建議、不該當硬關卡。這個過濾動作，最好也由獨立的人/AI 把關，因為「AI 寫的驗收標準可能本身就不可驗證」。

EARS：把驗收標準寫成可測試句型

EARS（Easy Approach to Requirements Syntax，Rolls-Royce 2009）是一套寫需求的固定句型，逼你把模糊的願望寫成有觸發條件、有明確反應的句子——天生好轉成測試。常用五種：

EARS 句型 → 直接對應 GWT / 測試
# Ubiquitous（恆常）
The system SHALL 永遠成立的規則。

# Event-driven（事件觸發）→ 最常用，直接變 When/Then
WHEN <觸發>, the system SHALL <反應>.

# State-driven（狀態）
WHILE <處於某狀態>, the system SHALL <反應>.

# Unwanted（錯誤處理）→ 對應「拒絕負數」那條
IF <非法情況>, THEN the system SHALL <如何拒絕>.

# Optional（選用功能）
WHERE <某功能啟用>, the system SHALL <反應>.
套到折扣計算機 → 每句都能驗
# Event-driven
WHEN a discount of 20% is applied to a base price of 100,
the system SHALL return a final price of 80.00.
  ↳ Evidence: dotnet test --filter discount_standard

# Unwanted behaviour
IF the base price is negative,
THEN the system SHALL reject the calculation with an error.
  ↳ Evidence: dotnet test --filter discount_reject_negative
💡 看出來了嗎？EARS 的 WHEN…SHALL… 幾乎逐字對應 OpenSpec 的 WHEN / THEN scenario、再對應 Reqnroll 的 When / Then 步驟、再對應一條 dotnet test --filter。從「模糊願望」到「會 pass/fail 的指令」，EARS 把這條翻譯路鋪平了。
06

最陰險的問題：AI 寫出「會過的假測試」

你最初的焦慮就在這。如果 Copilot 自己寫測試，它可能寫一個恆真、或 mock 掉關鍵邏輯的測試——綠燈很漂亮，但什麼都沒驗到。研究找到一個真實、確定性的解法：突變測試 Stryker.NET。

原理：Stryker 故意把你的程式改壞（一個個小變動，叫「突變體 mutant」），再跑你的測試。同一個突變，遇到好測試會被「殺死」，遇到爛測試會「存活」——差別不在突變，在你的測試夠不夠硬。

✓ 好測試 → MUTANT KILLED
突變：price*(1-pct/100) → price*(1+pct/100)

測試斷言 結果要等於 80.00。被改壞後算出 120 ≠ 80 → 測試變紅，突變被殺死。代表這條測試真的在盯規格。✅

✗ 爛測試 → MUTANT SURVIVED
同一個突變：price*(1-pct/100) → price*(1+pct/100)

但測試只斷言 結果不是 null（恆真的假測試）。改壞後算出 120 仍然不是 null → 測試還是綠的，突變存活。⚠️ 報告精準點名這條是裝飾品。

💡 這就是我們前面說的「把實作改壞，測試會不會變紅？」那道檢查題——Stryker 把它自動化、規模化了。Microsoft Learn 提醒：別追求 100% 突變分數，聚焦高風險邏輯就好。
07

可追溯鏈：從一句規格到一個綠燈

「確保 spec.md 被符合」最終長這樣——一條任何人都能指著看的鏈。任一環斷掉，CI 就擋住合併。

spec.md：Requirement→ #### Scenario→ Pricing.feature→ PricingSteps.cs
PricingService（實作）→ dotnet test 綠燈→ PR 綠勾 ✓
08

Agent A 的 context 快滿了怎麼辦？

LLM 的上下文窗有物理上限，改幾輪就會塞滿、開始「趕工收尾」（Anthropic 稱之為 context anxiety）。但在這套流程裡，這個問題大半被架構化解了——因為真相不在對話裡，在硬碟上。

✕

不要做的事：在同一個塞滿的 session 裡硬撐

上下文被前幾輪失敗方案污染後，越改越歪。Claude Code 官方建議：修正超過兩次還是錯，清空重來比繼續修好。

✓

該做的事：開一個全新的 Agent A，從硬碟重讀

因為 proposal.md / spec.md / tasks.md 全都寫在硬碟上的 markdown，新 session 直接讀檔就接上了——不需要繼承舊對話的雜訊。spec 就是它的記憶。

💡 這正是 spec-driven 的核心好處：把記憶從「會塞滿、會遺忘的對話」搬到「不會消失的檔案」。有來源直接說，這解決了長對話的「災難性遺忘」問題。tasks.md 的打勾狀態還告訴新 agent「做到哪了」，無縫接棒。
📌 對應我們最早的主題：這就是 harness 的記憶層。Agent context 滿不滿，不該是你的痛點——只要真相在硬碟上、且被 validate/CI 守著，換誰來接、換幾個 session 接，都跑同一份合約。
帶走這一句

spec.md 不會自己「被符合」。
是你疊的四道關卡，讓不符合的程式
連 main 分支的門都摸不到。

第 1 層靠 AI 自律（不可靠）；第 2~4 層靠機器判定（可靠）。
Harness engineering 的判斷力，就是知道哪一條該交給機器、哪一條只能靠人看。🌱
